## 3. Theming

### 3.1 The current state is not "unthemed" — it is inconsistent

Measured across `apps/mobile/src`:

- **116 colour literals**, **13 distinct colours**, in 7 per-file `StyleSheet.create` blocks
  (`#E6E6E6` ×24, `#7FB2FF` ×18, `#8A8A8A` ×14, `#FF7A7A` ×11, `#5A5A5A` ×9, `#2A2A34` ×9,
  `#101014` ×8, `#1B1B22` ×7, `#7DFF9B` ×5, `#FFC46B` ×4, `#26262E` ×4, `#16161C` ×2, `#6E6E6E` ×1).
- `app.config.ts` already declares **`userInterfaceStyle: "automatic"`** — the app tells iOS it
  supports both appearances.
- `_layout.tsx` wraps the `Stack` in `Auth0Provider` and `ConversationProvider` and **nothing else**.
  There is no theme provider, so the navigation headers render with the router's **default (light)**
  theme.

So on a device in light mode today: **light headers above hard-dark content**, on every screen that
sets `headerShown: true` — which is all five learner screens. That is not a polish item, it is a
visible defect, and it exists *now*.

### 3.2 What transfers from the web, and what does not

`docs/2026-07-03-light-dark-theme-support.md` settled three things that transfer as **decisions**:

- **Three-state** (System / Light / Dark), default **System**, resolving to **Dark** when the OS
  expresses no preference.
- Semantic tokens, not raw hexes at call sites.
- A defined light palette rather than "invert the dark one".

None of its **mechanism** transfers: the FOUC pre-paint script, `data-theme` on `<html>`, the
`localStorage` cross-tab sync and `next-themes` are all browser problems. React Native has
`useColorScheme()` and no flash to prevent.

The web's light palette values are the starting point for ours (they were tuned for contrast), and
the existing dark hexes above are already the dark half — this is a re-keying job, not a design job.

### 3.3 The shape

One `src/theme.ts` exporting a `Palette` type and two palettes, plus a `useTheme()` that reads
`useColorScheme()` and the stored override. Screens build their styles per scheme:

```ts
const styles = useMemo(() => makeStyles(theme), [theme]);
```

`StyleSheet.create` is static, so a per-scheme factory memoised on the palette is the mechanical
answer — 7 screens, one edit each, no new dependency.

Empty states move to `ContentUnavailableView` at the same time (D74): it is already proven on the
collection, and it themes itself, which removes six more colour decisions rather than re-keying them.

### 3.4 Three filters that correctly show nothing

`fav=1` (zero favorites), `kind=sentence` (zero rows) and every category (zero facets) are all
correct and all empty (S6 §13). **Do not "fix" them.** If the emptiness is worth softening, the honest
fix is a count beside each filter row, from data the facets query already returns — not hiding
controls whose emptiness is a fact about the collection.

## 4. Navigation

**The session-vs-navigation question is already answered** and must not be reopened: S4's D41 ends a
running session when the tutor screen unmounts, because `ConversationProvider` sits above the router
and `UIBackgroundModes: ["audio"]` means iOS will not stop it. That is the single most expensive bug
this project has designed out; leave it alone.

What is left is D65's tab bar. **Both options ship in `expo-router@57.0.12`:**

| | `Tabs` | `NativeTabs` |
| --- | --- | --- |
| Import | `expo-router` | `expo-router/unstable-native-tabs` |
| Implementation | JS tabs | real `UITabBarController` |
| Extras | — | SF Symbol icons, badges, `BottomAccessory`, minimize behaviour |
| API stability | stable | **`unstable-` in the import path** |

**Take `Tabs`** (D73). S7's gate is the word *shippable*, the tab bar is the chrome every screen hangs
off, and `unstable-` is the maintainer telling you the API will move. `NativeTabs` is the obvious
post-v1 upgrade and the badge support is genuinely attractive — record it, do not take it now.

Two tabs: **Lessons** and **Words**. `auth` and `probe` stay reachable from the lessons footer where
they already are.

## 5. Shipping

### 5.1 The pipeline has never run — and it goes first (D68)

S0 shipped on internal distribution (D9). The store leg — distribution certificate, an App Store
Connect record, a store-signed upload, processing, TestFlight — **has never been exercised**.

**The mechanics are already written**: [`apps/mobile/credentials/Apple-app-register.md`](../apps/mobile/credentials/Apple-app-register.md) is a
click-by-click runbook with a value inventory, and this file does not re-argue any of it. What S7
adds is the three things in *our* config that are still wrong:

- `eas.json` → `submit.production.ios` has **`appleTeamId` only**. `appleId` and **`ascAppId`** (the
  numeric App Store Connect id, which does not exist until the app record does) are missing;
  `ascAppId` is what makes `eas submit` non-interactive.
- `appVersionSource: "remote"` and `autoIncrement: true` (production profile) have **never run** —
  both existing builds were `build#1` from the preview profile. The failure mode is a second upload
  rejected for a duplicate `ios.buildNumber`, which reads like a signing error.
- `version: "1.0.0"` in `app.config.ts` is the marketing version and is fine; the build number is
  EAS's to manage once the above runs.

Budget for Apple-side latency no other stage has had: **5–30 minutes of processing per upload**.

**Internal TestFlight only for v1** (D76). External distribution additionally needs Beta App Review
and a filled-in Test Information section, and buys nothing while the tester list is one person.

### 5.2 🔴 The privacy manifest — an automatic rejection (D69)

**Expo does not generate `PrivacyInfo.xcprivacy`.** It must be declared as `ios.privacyManifests` in
the app config, and Apple emails a rejection within minutes of an upload that is missing required
reason codes. Our `app.config.ts` has no such key.

Worse, the declarations cannot simply be inherited from the pods: Apple's tooling does not correctly
parse the manifests that static CocoaPods dependencies ship, so **the app must repeat them**.

Derived by reading every `PrivacyInfo.xcprivacy` in our installed tree (10 files):

| Package                                | Category            | Reasons          |
| -------------------------------------- | ------------------- | ---------------- |
| `expo-file-system`                     | `FileTimestamp`     | `0A2A.1`, `3B52.1` |
| `expo-file-system`                     | `DiskSpace`         | `E174.1`, `85F4.1` |
| `expo-device`                          | `SystemBootTime`    | `35F9.1`         |
| `expo-constants`, `expo-system-ui`, `react-native` | `UserDefaults` | `CA92.1`   |
| `react-native` (core)                  | `FileTimestamp`     | `C617.1`         |

So the block to add is four categories with the **union** of the reason codes:

```ts
ios: {
  privacyManifests: {
    NSPrivacyAccessedAPITypes: [
      { NSPrivacyAccessedAPIType: "NSPrivacyAccessedAPICategoryFileTimestamp",
        NSPrivacyAccessedAPITypeReasons: ["0A2A.1", "3B52.1", "C617.1"] },
      { NSPrivacyAccessedAPIType: "NSPrivacyAccessedAPICategoryDiskSpace",
        NSPrivacyAccessedAPITypeReasons: ["E174.1", "85F4.1"] },
      { NSPrivacyAccessedAPIType: "NSPrivacyAccessedAPICategorySystemBootTime",
        NSPrivacyAccessedAPITypeReasons: ["35F9.1"] },
      { NSPrivacyAccessedAPIType: "NSPrivacyAccessedAPICategoryUserDefaults",
        NSPrivacyAccessedAPITypeReasons: ["CA92.1"] },
    ],
  },
}
```

⚠️ **`expo-sqlite`, `expo-crypto`, `@livekit/react-native`, `@livekit/react-native-webrtc` and
`react-native-auth0` ship no manifest at all.** That is either "they touch no required-reason API" or
"they have not declared". Re-run the `find node_modules -name PrivacyInfo.xcprivacy` sweep after any
dependency upgrade — the list above is a snapshot of an installed tree, not a law.

### 5.3 🔴 Store metadata, and the two URLs that do not exist (D70)

**App Store Connect requires a privacy policy URL and a support URL.** The web app has no
`/privacy` and no `/support` route — checked. Two static pages on the existing Next app are the
cheapest correct answer, and the privacy policy has real content to state because this app genuinely
ships user speech to a third party.

The privacy-label inventory, from what the app actually does:

| Category                            | Collected                          | Why                                        |
| ----------------------------------- | ---------------------------------- | ------------------------------------------ |
| Contact info → **Email address**    | yes, via Auth0                     | account / App Functionality; linked to identity |
| Identifiers → **User ID**           | yes, the Auth0 `sub`               | every row is owner-scoped by it            |
| User content → **Audio data**       | yes — the microphone stream        | the tutor conversation, sent to ElevenLabs |
| User content → **Other**            | yes — words, transcripts, summaries | the whole product                          |
| Diagnostics                         | **no**                             | nothing is shipped (D75)                   |
| Data used for **tracking**          | **no**                             | there is none                              |

Third parties that receive learner data and must be named in the policy: **ElevenLabs** (audio +
transcripts), **Anthropic** (word text, for the level and enrichment jobs), **Supabase** (storage),
**Auth0** (identity), **LangSmith** (traces, when enabled), **Vercel** (hosting).

Age rating: 4+. Category: Education.

### 5.4 Guideline 2.5.4 — the named risk, and the notes that clear it (D76)

Apps declaring the `audio` background mode are routinely rejected when the reviewer cannot hear
background audio. **Ours genuinely produces it** — that is what S1 measured on hardware — but the
reviewer has to *reach* it, and reaching it requires signing in.

Two cheap things, and skipping either is a predictable extra review cycle:

- **A demo account, pre-populated.** It must already contain **at least one lesson with several
  words**. A reviewer who signs in to an empty account has to invent a lesson before anything can be
  demonstrated, and the audio they are looking for is three steps past that.
- **Review notes that name the steps.** Draft:

  > This app is an English speaking tutor. The conversation is a live two-way voice session, which is
  > why the audio background mode is declared: the lesson must keep running while the screen is
  > locked, exactly as a phone call does.
  >
  > To hear background audio:
  > 1. Sign in with the demo account below.
  > 2. Tap the first lesson in the list.
  > 3. Tap "Start conversation" and allow microphone access when prompted.
  > 4. Say hello — the tutor replies out loud.
  > 5. **Lock the screen (side button).** The tutor keeps speaking and keeps listening; speak again
  >    and it answers with the screen still locked.
  >
  > Demo account: <email> / <password>
  >
  > Microphone use is the conversation itself. Audio is streamed to ElevenLabs for speech
  > recognition and synthesis; transcripts are stored against the learner's account so lessons can
  > be reviewed. Privacy policy: <url>

Step 5 is the one the reviewer must be told to perform, because nothing on screen suggests it.

## 6. Crash and error reporting — deliberately none (D75)

No Sentry, no Bugsnag, no Crashlytics, and none added. Three reasons, and the third is the real one:

1. The tester list is one person who can reproduce and report directly.
2. Adding an SDK now means a native rebuild, a new privacy-manifest sweep (§5.2) and a new entry in
   the data-collection labels (§5.3) — a whole extra column of submission risk on the stage whose
   job is to submit.
3. **The failures this app actually has are already observable server-side.** A session that dies
   leaves a `lesson_sessions` row with a short transcript; the post-call webhook enriches or does
   not; the level and enrichment jobs' failures are visible as null columns. The device is not where
   the interesting evidence lives.

What stays instead: the **`/probe` screen** (S4 D43) — drift, `AppState`, uplink/downlink counts —
which is the instrument for exactly the class of failure a crash reporter would not catch anyway.

Revisit when there is a second tester who cannot be asked what happened.

## 7. The two carried unknowns

### D77 — settle `sendContextualUpdate` here

S4 handed it over as "reported working, not measured"; S5 explicitly declined to settle it (D54)
because it had no resume path and forcing one in would have added a second risk to a stage measuring
neither. **S7 touches the tutor screen for theming anyway**, so the measurement is finally free:

Start a session, say two things, force-quit mid-sentence, reopen, take the recovery card's "Continue
that session". Expect **two `lesson_sessions` rows with two different conversation ids**, and the
tutor's first sentence after the reconnect continuing rather than greeting. That is the whole test.

### D78 — the `expo-doctor` drift

Seven packages are behind their SDK-57 patch versions (`expo-dev-client`, `expo-image`,
`expo-linking`, `expo-router`, and three more). Pre-existing since S5, and `expo-crypto` — the only
package this project added — is not among them.

**Do the upgrade, and do it first, before the store build.** `npx expo install --check` is the
supported path, they are patch-level moves within one SDK, and shipping a v1 that `expo-doctor`
reports as unhealthy makes every future failure ambiguous. It needs a native rebuild and a smoke
test on the device — which S7 is already doing for everything else. If any of them regresses,
record the pin and move on; what is not acceptable is carrying the warning into the store build
without a decision.

- `npx expo install --fix` exited non-zero *after* installing everything correctly. The retry it
  performs is why: this repo runs pnpm's `minimumReleaseAge` policy, so the fresh versions were
  refused once, an allowlist was written to `pnpm-workspace.yaml`, and the second attempt succeeded.
  The exit code is the first attempt's. **`pnpm-workspace.yaml`'s new `minimumReleaseAgeExclude`
  block is load-bearing** — deleting it as generated noise breaks `pnpm install` for everyone else.
- **The upgrade changed D73's answer under us.** `expo-router@57.0.13` deprecates the root
  `Tabs` re-export in favour of `expo-router/js-tabs`. Same stable component, and the decision is
  unchanged — but it is a live demonstration of why `unstable-native-tabs` was the wrong thing to
  hang every screen off.

### The theme

`src/theme.ts` is 12 tokens and two palettes. The dark palette is not new — it is the hexes the
screens already used, re-keyed by role. One merge: the lessons list's preview line was `#6E6E6E`, a
thirteenth grey used once and a shade off `faint`; it became `faint`. The light palette starts from
the web's `[data-theme="light"]` values, including the part that matters — the accent is `#4361EE`
and not the dark theme's `#7FB2FF`, which fails AA as link text on white.

Two shapes worth stating, because neither is the obvious one:

- **No provider, and no new dependency.** The override is a module-level store read through
  `useSyncExternalStore`, sitting beside `useColorScheme()` rather than above it. It persists through
  `expo-sqlite/kv-store`, which the app already depends on and which offers **synchronous**
  accessors — so the stored choice is known before the first paint. That is the native shape of the
  problem the web solves with a blocking `<head>` script.
- **`ThemeProvider` is imported from `expo-router`.** Not `@react-navigation/native` — see D72 and
  §9's table. The navigator theme is built by spreading `DefaultTheme`/`DarkTheme` so `fonts` (a
  required field, and nothing to do with colour) survives, and `card` is set to the screen
  background so the header is flush rather than a distinct band.

`StatusBar` was added at the same time: without it the clock keeps its light glyphs and disappears
into a white header. It is the same defect as the light-headers-on-dark-content one, one row up.

### Navigation

Three layout files and three `git mv`s. Each tab is a route **group** with its own `<Stack>`, so the
tab bar persists over a pushed lesson or word and each tab keeps an independent back stack.

**The URLs are unchanged, and that was checked rather than assumed** — the generated typed-routes
file lists exactly `/`, `/auth`, `/probe`, `/lesson-items`, `/lesson-items/[id]`, `/lessons/[id]`,
`/lessons/[id]/words`, the same seven as before. No group segment leaked.

Both tab stacks declare `unstable_settings = { anchor: … }`. The Words tab needs it: it has no
`index.tsx` because its root screen is `/lesson-items`, and without an anchor the router infers a
root from file order — which can land the tab on `lesson-items/[id]` with no id.

The lessons header's "Words" button is gone, and `auth` / `probe` stay on the root stack, so they
cover the tab bar rather than appearing inside a tab. They are an account screen and an instrument.

### One deviation from the plan: D74 is three empty states, not six

§1 counted "six of seven screens still use muted `Text` for empty states". Read closely, that count
includes notes that are **not** empty states: the word detail screen's "In no lesson right now." and
"Details are being prepared…" are notes inside one section of a populated page. A
`ContentUnavailableView` there would be a full-bleed illustrated block announcing that one of four
sections is empty. They stayed as themed muted text, with a comment saying why.

The three genuine screen-level empty states — lessons, lesson words, and the tutor transcript — all
moved to the shared `EmptyState`. It is worth more than the count suggests: the SwiftUI view takes
its type scale, icon tint and secondary-label colour from the system, so those three screens got
correct light-mode empty states **without adding a single token**.

Its `Host` has a **fixed height**, deliberately. `ContentUnavailableView` expands to fill whatever
SwiftUI gives it, so `matchContents` has nothing finite to measure — and every caller is a list's
`ListEmptyComponent`, where measuring to zero renders blank. Related to D3's trap, and answered the
same boring way.
