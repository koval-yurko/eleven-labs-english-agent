## Why this file is empty

S7 is the accumulated tail of every earlier stage: which error states turned out to be reachable,
which empty states exist, what the reviewer must be walked through, and what the App Review risk
actually is given how S1 resolved. None of that is knowable in advance — a S7 plan written today would
be a generic checklist, and the value of this stage is entirely in the specifics.

## Already decided — do not re-derive

- **App Review guideline 2.5.4 is the named risk.** Apps declaring the `audio` background mode are
  routinely rejected when the reviewer cannot hear background audio. Ours genuinely produces it, but
  the reviewer must _reach_ it: sign in, start a lesson, background the app. **Mitigation: a demo
  account plus explicit review notes describing exactly how.** Cheap, and skipping it is a predictable
  rejection.
- **Mic-permission denial surfaces as a session error**, not a pre-flight prompt (creation doc §4) —
  the copy must name that case rather than saying "check your settings".
- **iOS only** (D2). No Android device matrix, no Core-Telecom.
- **`format-date.ts` is not ported** — the user's real locale and timezone are the correct answer on a
  phone; the web helper exists only so SSR and hydration agree.

## ⚠️ S7 now owns an unproven prerequisite (D9, 2026-08-13)

S0 shipped on **internal distribution only**. The Apple leg — a distribution certificate, an App Store
Connect record for `work.kovalchuk.yurii.english-tutor`, a store-signed upload, processing, TestFlight
— has **never been exercised**. See [S0 §2, D9](./2026-08-13-expo-s0-scaffold-testflight.md#d9--testflight-deferred-to-s7-s0-ships-on-internal-distribution-).

That inverts this stage's shape. S7 was planned as the accumulated polish tail; it now begins with a
pipeline bring-up that S0 was originally meant to retire, and **that bring-up must happen first**,
because App Review risk (guideline 2.5.4, below) cannot be assessed until an upload exists at all.

- [ ] **Do the upload before the polish.** An empty-ish build that reaches TestFlight is worth more
      than a perfect build that has never been signed for the store.
- [ ] `eas.json` carries `appVersionSource: remote` + `autoIncrement` on the production profile and
      **neither has ever run** — both preview builds were `build#1`. The failure mode is a second
      upload rejected for a duplicate `ios.buildNumber`, which reads like a signing error.
- [ ] `submit.production.ios` has `appleTeamId` only. `appleId` and especially **`ascAppId`** (the
      numeric App Store Connect id, which only exists once the record does) are still to be filled in;
      `ascAppId` is what makes `eas submit` non-interactive.
- [ ] Budget for Apple-side latency that no other stage has: processing is 5–30 minutes per upload,
      and an **external** TestFlight group additionally needs Beta App Review.
